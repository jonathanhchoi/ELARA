## Objective

Conduct an exhaustive, skeptical literature review of the selected project using sources actually retrieved and read. Compare the closest published and unpublished work with the project's claimed contribution rather than merely its topic, identify ways the project could remain distinct, and give the researcher a verified preemption record and honest verdict.

## Prerequisite checks

1. Read AGENTS.md and PROJECT_STATE.md, then confirm an approved Stage 00 charter and an explicit selected-project decision. Stage 01 may be skipped only if that skip and the researcher-supplied project are recorded.
2. Restate the selected question, intended data, method, comparison, and claimed new contribution. If any element is indeterminate enough to change search results, obtain clarification before starting.
3. Load earlier conception sources only as leads. Reopen and independently verify them; an earlier citation or screen is not evidence for this stage.
4. Confirm current live web access. If key subscription databases are unavailable, the review may proceed only if it prominently identifies what could not be accessed and gives the researcher the exact searches to run; it may not claim completeness.
5. Confirm that `python scripts/build_preemption_review.py --help` succeeds and that the host can compile LaTeX and render PDF pages for visual inspection. If the researcher expressly selected Word or another format, confirm that format's builder and renderer instead. A missing compiler or renderer is an environment gap, not permission to activate an uninspected report.

## Researcher decisions

The researcher decides:

- whether a partially preempted project should distinguish, extend, narrow, combine, or stop;
- whether inaccessible database results must be supplied before accepting the verdict;
- which doctrinal and disciplinary lines of prior literature define the claimed contribution; and
- whether the remaining contribution justifies a feasibility audit.

The agent may recommend a disposition but must not approve novelty or silently reshape the project.

## Work

1. Allocate a unique run ID, record the exact project-file versions currently in use and the search question, and append a ledger start. Assume the project is preempted and try to prove it.
2. Before planning the full set of searches, run a short preliminary check — about thirty minutes, without the full search plan, calculations used to verify that files have not changed, or independent review. Confirm from live sources that the proposed collection exists at a named authoritative source, that a public sample or page describing the collection is reachable, and that no obvious license or terms restriction blocks the planned use. When Stage 01 was skipped, also apply the Stage 01 selection tests to the researcher-supplied project: the question is statable in one sentence, either plausible result is interesting, the task determines values from supplied text rather than predicting an outcome beyond that text, the variables look verifiable from single documents, and execution is plausible in weeks rather than years. Record a one-page pass/fail note with the check links in the record of the run and give it to Stage 03 so the full data gate does not repeat these checks. A failed preliminary check stops with `waiting_for_user` or routes to `01-conceive` before any exhaustive searching begins; it never silently reshapes the project.
3. Plan combinations of search terms spanning the question, synonyms for each concept, unit, jurisdiction, period, collection, method, claimed result, leading cases or statutes, and citation chains. Log every query verbatim, with route, timestamp, result count when available, and disposition.
4. Run at least fifteen genuinely distinct queries, broad before narrow, across at least four suitable routes: scholarly search or OpenAlex; law-school repositories and law-review sites; SSRN and working-paper title searches; relevant disciplinary indexes or repositories such as NBER, OSF, arXiv, SocArXiv, or institutional archives; and the open web for conference programs, symposia, calls, datasets, dissertations, and works in progress. Use available subscription databases only within the researcher's authorization. Run the queries, author searches, citation chains, retrievals, and the fresh review as research fan-outs under `workflow/shared/observation-fanout.md` ("Research fan-outs" and "Worker tool surface, time boxes, and crash-resume"): for each wave, write one brief per query, author, chain, or work and a `spec.json` under `project/sources/preemption/<run_id>/fanout/<wave>/`, seal it with `python scripts/research_fanout.py prepare`, and hand the directory to the host's orchestrator — in Claude Code the saved `elr-research-fanout` workflow, launched by the assistant; in Codex the kit's `elr_research_worker` sub-agents, spawned by name in bounded waves — never an all-tools agent, never one hand-launched worker at a time, never a serial imitation in the parent's context. The controller records launches, bounds attempts, and reports what is pending, so a wave interrupted by a crash resumes from the files; after each wave the parent validates the returns, merges them into the search log and candidate list, and appends a ledger checkpoint. A worker that meets a 401/403/429, CAPTCHA, bot challenge, or login wall records a typed access gap and moves on. For every potentially material work whose full text remains blocked, the parent then runs the parent-only browser fallback in `workflow/shared/observation-fanout.md`: try lawful open routes first, then use browser control in the researcher's main authorized session for one bounded ordinary-UI retrieval attempt. The parent, never a worker, logs route `parent_browser_fallback`; unresolved sources feed the manual search packet in step 11.
5. Once close authors appear, search each author's publication page, CV, repository, coauthors, datasets, and related papers. Follow backward and forward citations and inspect relevant review articles. Rank by substantive proximity and importance, not title similarity.
6. Continue until three consecutive well-designed new queries yield no previously unseen close work. Record those queries; do not stop merely because a preferred answer emerged. One early exit exists: if a retrieved and fully read work decisively occupies the same thesis, evidence, and contribution, the review may end early — retrieve that work, record the value used to verify that its file has not changed, obtain a fresh independent review, test whether the project could remain distinct, mark the review `truncated on decisive preemption`, and go straight to the `preemption-disposition` gate. Such an early-ended review cannot support a later `open` verdict or a repositioned project without a full rerun.
7. Retrieve each work relied upon. Save lawful full-text copies under the run directory and hash them. For every item, record full citation, persistent and landing URLs, access date, publication status, venue, retrieval status, retrieval surface (including `parent_browser_fallback` where used), full-text-read status, local path, and whether it is verified or unverified. Validate a browser-downloaded file as the identified work rather than a challenge or error page before hashing and reading it. A snippet, abstract, another paper's citation, or model memory cannot make an item verified.
8. Create claim_evidence.csv linking every substantive description and preemption claim to the source ID, page or section, and a short supporting quotation. Stay within lawful quotation limits. If full text cannot be reached, label the attribution unverified and give the researcher the exact title, locator, database, and query needed.
9. Construct the detailed review of the closest works. For each, state its actual question, data, method, thesis, publication status, and precisely why it does or does not occupy the same contribution. Treat working papers, forthcoming articles, dissertations, active datasets, and legal developments that make the question obsolete as current threats to the contribution.
10. Render one verdict: preempted, partially preempted, or open. Before preempted, test whether the project could distinguish itself, extend the work, cover a new period or set of courts, use a new scale or measurement, or address limitations the prior authors acknowledged. Before open, run and log a final skeptical search designed to disprove novelty. State discoveries that would change the verdict and report no confidence score.
11. Report an honest contribution sentence, relevant lines of prior literature, scoop risk, active researchers, inaccessible routes, exact searches requiring researcher access, check date, and recommended recheck date. Record the recheck date and the scoop-risk level in the `preemption-disposition` approval record's conditions so Stage 04 can check the review's age mechanically.
12. Give the draft and evidence table to a fresh reviewer with no stake in the conclusion (per `workflow/shared/fresh-review.md`). The reviewer must reopen every cited URL, validate bibliographic identity and attributed claims, sample archived files and hashes, and challenge the verdict. Correct factual errors; move failures to unverified; preserve the review trail.
13. Instantiate `workflow/templates/preemption_review_template.md` as the run-specific `project/runs/<run_id>/preemption_review_source.md`. Preserve the required section order and complete every descriptive field at the top. Begin with a decision-focused executive summary centered on direct comparisons between the intended contribution and every closest match that materially affects the verdict. State the intended contribution exactly. For each closest match, state what the work actually says, its relevant scope and evidentiary or methodological basis, the precise component of the intended contribution it occupies, what remains distinguishable, and the source-list ID, IDs from the table linking claims to evidence, or pinpoint pages supporting that comparison. Then synthesize the remaining contribution, recommended disposition, scoop risk, material access gaps, and recheck date. Do not treat topical similarity alone as preemption, group materially distinct works into one comparison, or introduce a claim or source absent from the verified detailed review. Keep the summary within roughly two or three rendered pages and the builder's 1,200-word limit. Unless the researcher expressly selected another format, generate `project/artifacts/preemption_review_vNNN.tex` with `python scripts/build_preemption_review.py project/runs/<run_id>/preemption_review_source.md project/artifacts/preemption_review_vNNN.tex`, compile it to `project/artifacts/preemption_review_vNNN.pdf`, and preserve the build log. If the researcher selected Word, pass a `.docx` output path to the same builder and record that preference. The Markdown file is the reviewable build source, not the researcher-facing report. Render the complete PDF or expressly selected alternative under `project/runs/<run_id>/rendered_preemption_review/`, inspect every page at 100 percent zoom, and iterate on the source until headings, paragraphs, lists, hyperlinks, page breaks, headers, and footers are clean. Never patch generated `.tex`, PDF, or DOCX output by hand. If the required compiler or renderer is unavailable, record what is missing, do not record the report as the version currently in use, and set `waiting_for_user` with the exact capability needed.

## Artifacts

`preemption_review_vNNN.pdf` is the default researcher-facing literature review, compiled from the versioned LaTeX source. An expressly requested alternative such as DOCX may be used instead, with the preference recorded. The report must contain, in order, the concise executive summary, detailed review of the closest work, verdict and what would change it, positioning in prior literature, scoop risk, search methods and evidence that additional searching had stopped producing new results, access limitations and searches requiring researcher access, and review date. The detailed review begins on a new page after the executive summary. The run-specific `preemption_review_source.md` is the exact build source and is preserved unchanged when the run closes. The source list, query-level search log, table linking claims to evidence, retrieved copies, rendered page images, and record of the run are mandatory supporting files. Do not cite a source absent from the source list.

## Verification

- Confirm the preliminary check ran and its pass/fail note is in the record of the run, and that the minimum query, route, author-search, citation-chain, and stopping requirements hold from the search log — or, for a review ended early because decisive prior work was found, that the decisive work was retrieved, read, checked for later changes, and independently reviewed and that the early ending is stated prominently in the review.
- Confirm that the executive summary appears first and makes the closest-match comparisons its substantive center. For each work that materially affects the verdict, confirm a separate comparison states what the work actually says, its relevant scope and basis, the exact component of the intended contribution it preempts, what remains, and the source-list and claim-evidence IDs or pinpoint pages. Confirm the synthesis does not mistake topical overlap for preemption, contains no claim or source absent from the detailed review, stays within 1,200 words and approximately three rendered pages, and is followed by a clean page break before the detailed review of closest work.
- Confirm that every potentially material 401/403/429, CAPTCHA, bot-challenge, login-wall, or automated-download failure was either resolved through a lawful open route, given one parent browser-control attempt recorded as `parent_browser_fallback`, or assigned a reason why browser retrieval was unavailable, unauthorized, or unsafe (a challenge-evidenced host under the fallback protocol in `workflow/shared/observation-fanout.md`). Confirm that no worker received an interactive tool and that every unresolved item appears in the access limitations and searches requiring researcher access.
- Reopen every cited URL and confirm that every verified work was actually read and every substantive attribution has pinpoint evidence.
- Confirm that inaccessible sources remain unverified and that absence claims point to logged searches rather than intuition.
- Confirm that the verdict compares the claimed contribution rather than only the topic, explains how the project could remain distinct and what would change the verdict, and distinguishes topic overlap from the same question and evidence.
- Confirm the fresh review is archived or summarized in the run manifest and all discrepancies are resolved or disclosed.
- Confirm the LaTeX source compiles without errors, overfull boxes, unresolved references, or missing glyphs and that the PDF carries the required metadata and section hierarchy. For an expressly selected alternative, apply equivalent format checks. Confirm the report contains no unresolved template marker and was rendered after its last build. Inspect every rendered page for clipped or overlapping text, broken lists or tables, bad page breaks, missing glyphs, and inconsistent headers or footers. Record source and output hashes, build and render commands, tool versions, page count, and inspection result in the run manifest.
- Confirm no previous artifact, ledger row, source, or input was overwritten.

## State transition

Set current_stage to 02-preemption-review and status to running only when execution begins. If retrieval fails before a defensible review is possible, set status to waiting_for_user, list the inaccessible sources or databases, append exact counts, and keep prior active artifacts unchanged.

After verification, activate the new review, set status to awaiting_approval, mark preemption-disposition pending, and request an explicit proceed, reposition, return to conception, or stop decision. On proceed, append the accepted verdict and contribution sentence to DECISIONS.md, mark the gate approved, and set current_stage to 03-feasibility-audit and status to ready. A material repositioning requires a versioned targeted rerun of this stage; a rejected or preempted project returns to 01-conceive or the researcher-supplied selection path.

## Next-stage handoff

Tell the researcher the verdict, remaining access gaps, active review version, and date when novelty should be rechecked. After explicit acceptance, provide the exact next task: run 03-feasibility-audit using the accepted question, contribution, corpus, variables, and closest-work map, and stop at the feasibility go/no-go gate.
