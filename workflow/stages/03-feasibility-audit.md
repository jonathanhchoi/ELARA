## Objective

Test as cheaply as possible whether the accepted project should stop before resources are committed. Establish each feasibility fact with a current live check, identify the single limitation that controls the recommendation, estimate how many records remain after each access, screening, and coding step, assess the validation burden, estimate default sub-agent completion time and available resources, compare the cost of the optional API route, and return a go, go-with-modifications, or no-go recommendation for the researcher.

## Prerequisite checks

1. Read AGENTS.md and PROJECT_STATE.md, validate the approved preemption disposition, and load the exact selected question, claimed contribution, corpus, variables, method, and conditions from active artifacts and DECISIONS.md.
2. Confirm that the question has not materially shifted since Stage 02. A new question, population, corpus, or contribution must be rechecked for preemption.
3. Confirm live access to the proposed data source, the host's sub-agent capacity, current provider documentation and prices for the API comparison, and any APIs or repositories required for probes. Do not fill a failed probe from memory.
4. This is not data authorization. Inspect only public samples or metadata whose use is clearly permitted for this audit. Do not send licensed, confidential, restricted, or human-subjects text to any hosted model before Stage 06 approval.
5. Define in advance the cheapest probe likely to reveal a fatal flaw. Record planned limits so the audit does not become an unapproved corpus run.
6. Confirm that `python scripts/build_feasibility_audit.py --help` succeeds and that the host can compile LaTeX and render PDF pages for visual inspection. If the researcher expressly selected Word or another format, confirm that format's builder and renderer instead. A missing compiler or renderer is an environment gap, not permission to activate an uninspected report.

## Researcher decisions

The researcher alone decides:

- whether both plausible result directions are sufficiently important;
- what target population and comparison the paper should speak to;
- whether a judgment-heavy construct should be decomposed, replaced, or abandoned;
- acceptable coverage gaps, selection risks, spending, time, and manual validation burden;
- whether a licensed, restricted, confidential, or human-subjects route is worth pursuing; and
- whether to accept go-with-modifications, return upstream, or stop.

Anything implicating terms, institutional rules, nontrivial spending, or risk is flagged, not resolved by the agent.

## Work

1. Allocate a run ID, record the input versions currently in use and the budget for live checks, and append a start row. Treat a well-evidenced no-go as a successful audit. Order the gates by the expected cost of finding a reason to stop: the questions that require no spending first, then the least expensive check likely to show that the project cannot work, then the spending gates.
2. **Gate 1: Is the coding task one that LLMs are good at?** The stable internal ID is `task-type`. Apply this question to every proposed LLM use. Classify it as estimation from supplied text or prediction. A prediction task fails absent a defensible target population, sampling procedure, and training-corpus leakage analysis; instructions to ignore learned knowledge are not a leakage control.
3. **Gate 2: Can a careful human verify each coding decision from the source?** The stable internal ID is `variable-verifiability`. Apply this question variable by variable. Ask whether a careful research assistant can determine the value from one supplied document, where possible by an exact quotation. State the verification method and likely coder disagreements. Red-flag holistic evaluations, expert taxonomies, novel constructs defined by model output, and cross-document inference. Propose observable components, but reserve construct choices for the researcher.
4. **Gate 3: Would this be an interesting contribution to the literature regardless of the direction of the results?** The stable internal ID is `either-way-contribution`. Write the most defensible headline under each result direction and identify who would care. Flag an expected or null direction that cannot support a contribution.
5. Run the precommitted least expensive check likely to show that the project cannot work from prerequisite check 5. If it fails, do not keep spending merely to rescue the idea: skip the remaining gates that require live checks, complete the question-led report, and recommend no-go. If it passes, test the next likely controlling limitation within the approved budget.
6. **Gate 4: Can we obtain and use the data the project needs?** The stable internal ID is `data-access`. Verify with live checks that the collection exists, its authoritative source and access route, dates and jurisdictions covered, document formats, available descriptive fields, selection layers, known gaps, duplicate identifiers, OCR quality, API behavior, rate limits, and current terms or license status. Pull a small, authorized sample and confirm it contains the information proposed for coding. Preserve the raw responses and record each failed check with its reason. Reuse the Stage 02 preliminary checks rather than repeating them. Record every unit whose content is inspected or coded during any check in `probe_exposure_manifest.csv` — unit or document identifier, hash where available, variables inspected or coded, and check ID — so Stage 04 can divide the data appropriately and Stage 13 can keep those units out of the held-out validation sample.
7. **Gate 5: Will there be enough usable data to answer the research question?** The stable internal ID is `base-rate-and-power`. Estimate the frequency of relevant records from authorized marker counts or a transparently coded mini-sample, never intuition, and add every mini-sample unit to `probe_exposure_manifest.csv`. Project how many records remain from the raw collection through availability, eligibility, readability, coding success, and analysis inclusion. Give low, central, and high scenarios and identify assumptions. Then compute the minimum detectable effect (the smallest effect the design is likely to distinguish from zero) for each planned primary comparison at a researcher-approved power and significance level — present 0.80 and 0.05 as defaults for explicit approval — under each scenario, inflated for anticipated coding errors and for clustering or design effects. Preserve the formula or script and its assumptions so Stage 04 and the preregistration can quote them. If the minimum detectable effect exceeds every effect size plausible against the closest literature, this gate fails: the design cannot answer its question, and the verdict should say so in plain language rather than deferring the discovery to analysis.
8. Budget human validation before scale-up. Specify a held-out design and size it from precision targets rather than a heuristic: for each key class, state the maximum acceptable confidence-interval half-width for the error rates the planned correction requires (present a default for researcher approval), derive the sample size from the data-availability scenarios, and treat a few hundred units as a floor, not a target. Budget independent double coding for a prespecified share of the sample — ordinarily ten to twenty percent — so human-to-human reliability can be measured at Stage 13. Carry the derived human-coding hours into the time and resources question. Keep prompt-tuning examples separate from the held-out set.
9. **Gate 6: Can the project be completed in a reasonable amount of time with the available resources?** The stable internal ID is `time-and-resources`. Use ELARA's software for coordinating parallel sub-agents as the default route for later coding. Do not assign a dollar value to subscription-backed sub-agent use. For low, central, and high scenarios, estimate elapsed completion time from the expected assignments, the recorded limit on simultaneous sub-agents, observed or tested per-assignment duration, retries, validation steps that must run one at a time, and the time needed to combine results. If an authorized timed check is unavailable, expose the unverified duration assumption and use a range. Express human validation and other resource burdens primarily as time or capacity requirements; record known fixed charges and flag potential spending decisions, but do not invent dollar estimates. Separately include a comparison of what the same work would cost through the optional API route in every audit. Label the API as an optional execution alternative rather than the default and explain that its per-token price is not equivalent to subscription-backed sub-agent use. Calculate the comparison from projected documents and tokens at each stage where records are screened out, current provider prices, retries, plausible model levels, and available batch discounts. Save formulas and price-sheet URLs with access dates; do not recall prices. When any candidate data route is licensed, restricted, confidential, or human-subjects, also estimate the authorization lead time — license negotiation, data-use agreements, IRB or ethics review — from current published evidence, include low, central, and high lead-time scenarios in the schedule range, and treat a lead time incompatible with the researcher's stated timeline as the controlling limitation.
10. **Gate 7: Could coding errors change the answer, and can the analysis account for them?** The stable internal ID is `measurement-error`. For each important variable and estimand, explain how false positives, false negatives, subgroup error, missing documents, and selective refusals could bias the estimate. Name a planned measurement-error correction or sensitivity analysis and the validation quantities it requires, following the protocol in workflow/shared/measurement-error-correction-guide.md: reason from the estimand and validation design, then verify candidate methods against current literature retrieved live — the guide's named estimators are dated leads, not a closed menu. The choice remains the researcher's. Accuracy alone is not a pass.
11. **Gate 8: Does a legal, ethical, data-use, or spending issue require the researcher’s decision?** The stable internal ID is `researcher-decision`. Identify every issue touching terms of service, licenses, institutional rules, restricted or human-subjects data, confidentiality, or nontrivial spending. Flag each issue for the researcher and do not resolve it or treat silence as approval.
12. Instantiate `workflow/templates/feasibility_audit_template.md` as the run-specific `project/runs/<run_id>/feasibility_audit_source.md`. Unless the researcher expressly selected another format, generate `project/artifacts/feasibility_audit_vNNN.tex` with `python scripts/build_feasibility_audit.py project/runs/<run_id>/feasibility_audit_source.md project/artifacts/feasibility_audit_vNNN.tex`, compile it to `project/artifacts/feasibility_audit_vNNN.pdf` with the available LaTeX tools, and preserve the build log. If the researcher selected Word, pass a `.docx` output path to the same builder and record that preference. The report must use one prose section for each gate, headed by the exact question above. Under each question, state the decision, evidence IDs, practical meaning, and conditions or next step. Do not use a gate table and do not display the internal IDs or earlier technical labels as headings. Name the single controlling limitation; the least expensive check likely to show that the project cannot work; how many records remain after each screening step; minimum detectable effects; sub-agent completion-time scenarios; the estimated optional API cost; risks; unverified assumptions; and a recommendation of go, go with modifications, or no-go. State exactly what evidence would change the recommendation and report no confidence score. The builder rejects a table, a missing or renamed question, an earlier technical gate heading, or missing labeled content. Render the complete PDF or expressly selected alternative under `project/runs/<run_id>/rendered_feasibility_audit/`, inspect every page at 100 percent zoom, and iterate on the Markdown source until the report is clean. Never patch generated `.tex`, PDF, or DOCX output by hand. If the required compiler or renderer is unavailable, record what is missing, do not record the report as the version currently in use, and set `waiting_for_user` with the exact capability needed.

## Artifacts

`feasibility_audit_vNNN.pdf` is the default researcher-facing decision document, compiled from the versioned LaTeX source. An expressly requested alternative such as DOCX may be used instead, with the preference recorded. The report must be narrative, not a gate table. Its eight sections must use the exact question headings in the Work section, while stable internal IDs remain available only for evidence links, structured records, and validation. The run-specific `feasibility_audit_source.md` is the build source and is preserved unchanged after the run. `probe_log.csv` records each live check, including its ID, hypothesis, method, URL or local source, access time, authorization basis, exact result, raw-output path, and interpretation. `probe_exposure_manifest.csv` lists every unit whose content was inspected or coded during the audit, so later stages can keep those units out of the validation sample reserved from development. `funnel_model.csv` shows the low, central, and high counts remaining after each screening and coding step. It and `cost_model.csv` must show assumptions and formulas — including the minimum-detectable-effect and validation-precision calculations — rather than only totals. Retain the `cost_model.csv` name for compatibility. It must distinguish the default sub-agent route from the optional API alternative and record the scenario, expected assignments, number of simultaneous sub-agents, observed or assumed duration, retries, steps that must run one at a time, projected completion time, and, for the API comparison only, token and current-price calculations. Mark the sub-agent dollar cost as not estimated, not zero. Record human and other resource requirements as time or capacity, plus known fixed charges where they exist. `variable_verifiability.csv` must cover every proposed variable. Preserve raw requests, responses, samples, screenshots where necessary, and a record of every missing item or failed check, with its reason, under `probes/`.

## Verification

- Reperform or independently inspect every fact that controls a gate; confirm each points to a dated live probe.
- Reconcile counts from the raw collection through analyzable observations and ensure failures remain explicit rows.
- Recalculate the low, central, and high sub-agent completion times from expected assignments, the limit on simultaneous sub-agents, observed or tested duration, retries, validation steps that run one at a time, and the time needed to combine results.
- Confirm the audit does not assign a dollar value to subscription-backed sub-agent use and includes a separately labeled estimate of the same work through the optional API route, using recorded current prices, token assumptions, retries, model levels, and available batch discounts.
- Confirm no restricted text was exposed before authorization and that all terms, license, confidentiality, and human-subjects issues remain flagged for Stage 06.
- Confirm validation is held out, sized from the stated precision targets, and budgeted (including the double-coded reliability subsample) and that proposed error correction matches the anticipated error.
- Recompute the minimum-detectable-effect calculations from the archived formula and confirm the verdict reflects them.
- Confirm every unit inspected or coded during a probe appears in the probe-exposure manifest.
- Confirm the LaTeX source compiles without errors, overfull boxes, unresolved references, or missing glyphs and that the PDF contains no tables, uses the eight exact question headings in order, contains no legacy technical gate heading, and carries complete decision, evidence, meaning, and next-step text for each gate. For an expressly selected alternative, apply equivalent format checks. Confirm the active report was rendered after its last build and inspect every page for clipping, overlap, broken lists, bad page breaks, and missing glyphs. Record the source and output hashes, build and render commands, tool versions, page count, and inspection result in the run manifest.
- Confirm the verdict follows the gate results, identifies the single controlling limitation, and contains every unverified assumption.

## State transition

At execution start, set current_stage to 03-feasibility-audit and status to running and append the run. If a live fact cannot be checked, set status to waiting_for_user, list the exact probe or access needed, and do not substitute an assumption.

After verification, activate the audit, set status to awaiting_approval, mark feasibility-go-no-go pending, and request an explicit go, go-with-modifications, no-go, or upstream-revision decision. On go, append accepted conditions to DECISIONS.md, mark approval, and set current_stage to 04-methods-design and status to ready. On modifications that change novelty, return to Stage 02; on a new idea, return to Stage 01. On no-go, record the stopping decision and leave the workflow waiting_for_user or superseded as directed; do not advance.
